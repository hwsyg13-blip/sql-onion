# 이론 본문 톤 가이드 — AdSense 거절 대응

작성: 2026-05-03 · 적용 대상: `src/data/theoryHtml.ts` (30개 챕터, 사이트 렌더링용 HTML 버전) + 사이트 메타

---

## 0. 목적

Google AdSense가 거절한 사유는 본문이 "AI가 만든 글"로 보여서가 아니라, **사이트 어디에서도 운영자/저자의 차별화된 관점이 보이지 않는다**는 점이다. 30개 챕터가 같은 4섹션 label-tag pill 템플릿(핵심 요약 / 개념 도식화 / SQL 실전 / Before & After)을 반복하고 있어 리뷰어 관점에서는 "scaled / templated content"로 분류된다.

본 가이드는 SQLD 시험을 직접 본 적이 없는 운영자가 **honest한 차별화 콘텐츠**를 만들기 위한 규칙을 정의한다. 1인칭 시험 후기 같은 fabrication은 금지하고, **운영자 시점 + 사이트 데이터 + 편집 의견**으로만 voice를 구성한다.

## 1. 가용한 차별화 source

| Source | 사용 가능 | 예시 |
|---|---|---|
| 사이트 사용자 데이터 | ✅ 활용 권장 | "이 챕터의 [기출 49회 23번]을 푼 사용자 중 38%가 ②번을 선택" |
| 회차 cross-reference | ✅ 활용 권장 | "비슷한 함정이 [55회 7번]에 다시 등장" |
| 운영자 편집 의견 | ✅ 활용 권장 | "이 절은 외우기보다 직접 SELECT를 쳐봐야 머리에 남음" |
| 사이트 운영 메타 | ✅ 활용 권장 | "이 사이트의 미니테스트는 ~ 기준으로 만들었다" |
| 1인칭 시험 후기 | ❌ 금지 | "내가 시험 봤을 때..." (fabrication) |
| 가공된 합격 anecdote | ❌ 금지 | "내 친구가 이 부분에서 떨어졌다" (fabrication) |

**핵심 원칙**: **저자 voice = 사이트 운영자 voice**. "내가 SQLD를 봤다"가 아니라 "이 사이트를 운영하면서 학생들의 풀이 데이터를 본다"는 입장.

## 2. label-tag 섹션 템플릿 다양화 (가장 우선)

### 2-1. 4섹션 동일 템플릿이 핵심 문제

지금: 30/30 챕터가 정확히 4개 label-tag pill로 시작·구성:

```
30회  핵심 요약
30회  개념 도식화
31회  SQL 실전
30회  Before & After
 5회  비교 (일부 챕터에만)
```

**폐지/변형 이유**: 모든 챕터에 같은 4개 라벨이 같은 순서로 박혀 있으면 "한 사람이 직접 쓴 글"이 아니라 "어떤 양식에 채워 넣은 글"로 보인다.

### 2-2. 변형 규칙

전 챕터 공통 4개 강제 X. 챕터당 **2~6개로 자연 변동**, 챕터 성격에 맞는 라벨로:

**개념 챕터(c111, c114, c115, c121 등)**:
- 핵심 요약 → "데이터 모델이란" / "정규화가 뭔지" 같은 챕터별 첫 라벨
- 개념 도식화 → 유지 가능 (단계/관계가 실제로 있는 챕터)
- SQL 실전 → 코드 예제가 짧으면 일반 prose로 흡수
- Before & After → 정규화·식별자 같이 비교가 핵심인 챕터에만

**SQL 문법 챕터(c212, c214, c216 등)**:
- 핵심 요약 → "SELECT가 뭐 하는지" 식으로 변형
- 문법 → 변형 → 실수 패턴 → 비슷한 다른 문법과 비교
- 개념 도식화 / Before & After 안 써도 됨

**함수 모음(c213, c223 등)**:
- 자주 쓰는 것 → 헷갈리는 짝 → 시험 빈출 → 학습자가 자주 틀리는 부분
- 4섹션 템플릿 통째로 안 써도 됨

같은 챕터끼리도 라벨 개수가 2~6개로 자연스럽게 변동되어야 함. **모든 챕터에 같은 4개가 박혀 있는 게 가장 큰 신호**.

### 2-3. label-tag pill 자체를 줄이는 방향도 OK

label-tag(노란/녹색 pill 헤더)을 모든 섹션에 다는 대신, 일반 `<h2>` 헤더로 두는 챕터가 있어도 됨. 디자인 일관성보다 "사람이 직접 썼다"는 인상이 우선.

## 3. 본문 prose 규칙

### 3-1. 표 보존, 표 주변 prose 두께 확보

표 자체는 study aid로 유지. 단, **표 단독 배치 금지**. 모든 표에:

- **앞**: 1~2줄 도입 — 왜 이 표를 보는지, 어떤 비교를 하는지
- **뒤**: 1~3줄 해설 — 표에서 어떤 행이 시험에 잘 나오는지, 학습자가 어떤 행에서 막히는지

```

| 관점 | 영문 | 모델링 대상 | ... |

(표만 있고 끝)
```

## 데이터 모델링의 3가지 관점

데이터 모델링을 하나의 활동으로 묶어서 보지 않고, 어떤 측면에서 보느냐로
나눠서 본다. 시험에서는 이 세 관점의 이름과 핵심 질문이 짝지어 출제된다.

| 관점 | 영문 | 모델링 대상 | 핵심 질문 |
| 데이터 관점 | Data | 엔터티·속성 | 무엇을(What) |
| 프로세스 관점 | Process | 업무가 하는 일 | 어떻게(How) |
| 상관관계 관점 | Interaction | CRUD 매트릭스 | 언제(When) |

이 사이트 미니테스트에서 상관관계 관점을 다른 두 개와 헷갈리는 비율이
가장 높다. "데이터·프로세스 상관관계"라는 긴 이름 때문에 데이터 관점이나
프로세스 관점의 일부로 착각하는 경우다. 셋이 별개의 관점이라는 점만
잡으면 시험 한 문제는 챙긴다.

### 3-2. 명사구 종결 비중 축소

**규칙**: 단락의 첫 1~2 문장은 **마침표 있는 서술형**. 표·리스트 다음 보충 단락도 마침표 있는 서술형. 표 안의 셀이나 bullet 안 짧은 라벨은 명사구 OK.

전 단락을 서술형으로 바꿀 필요는 없음. 챕터당 마침표 있는 서술 단락이 5개 이상이면 충분.

### 3-3. 자연 연결어 추가 (20/30 챕터 부족)

연결어 부족 챕터는 prose가 단절적으로 읽힘. 보강 키워드:

| 사용처 | 연결어 |
|---|---|
| 대비/전환 | 그런데, 하지만, 반면에, 다만 |
| 추가 설명 | 사실, 어차피, 그러니까 |
| 인과 | 따라서, 그래서, 결국 |
| 양보 | 단, 어쨌든, 그래도 |

각 챕터에 **5+개** 자연스럽게 분포. 억지로 박지 말고 prose 단락의 두 번째·세 번째 문장에 자연스럽게 들어가도록.

### 3-4. 운영자 voice 삽입 (가장 중요 — 30/30 챕터 0건)

**모든 챕터에 최소 2회**. 위치 자유 (서두, 표 다음, 챕터 끝 등):

| 형태 | 예시 |
|---|---|
| 사이트 사용자 데이터 | "이 사이트 미니테스트에서 이 OX의 정답률은 60%대로 떨어진다" |
| 회차 cross-ref | "기출 [49회 23번]에 같은 함정이 다시 등장한다" |
| 편집 판단 | "이 절은 외우려 하지 말고 직접 SELECT를 쳐봐야 한 번에 잡힌다" |
| 운영 메타 | "이 사이트의 미니테스트 OX는 학습자 오답이 가장 많은 포인트를 기준으로 만들었다" |
| 학습 가이드 | "이 챕터에서 학습자가 가장 자주 잘못 알고 있는 건 ~다" |

→ AdSense E-E-A-T(Experience/Expertise/Authority/Trust) 평가의 핵심 신호.

**자연스럽게 분산**: 챕터 서두에 한 번, 핵심 표 뒤에 한 번 정도. 챕터 끝에 몰아넣지 말 것.

## 4. 챕터 마무리

### 4-1. (참고) 30초 정리 / 시험 출제 포인트는 이미 분리됨

원본 markdown에는 `[시험 출제 포인트]`, `> **30초 시험 직전 정리**` 가 있지만, 사이트 렌더링 HTML(`theoryHtml.ts`)에는 빠져 있다. CheatSheetScreen으로 분리됨. **본 가이드에서 별도 작업 없음**.

### 4-2. 챕터 끝 스타일 다양화 (선택)

지금 HTML 버전 챕터 끝부분이 비슷한 ex-box / 강조 박스 패턴이면 일부 챕터는 마무리 없이 자연스럽게 종결, 일부는 "관련 기출 모아보기" 또는 "학습자가 자주 틀리는 부분" 같은 형태로 변형. 강제 X.

## 5. 챕터 길이 변별

지금 평균 4,200자, 표준편차 작음 — "기계가 균등하게 채운 흔적"으로 읽힐 여지.

**규칙** (강제 X, 자연스러운 결과로):
- **시험 빈출 + 학습자 오답 많은 챕터** (정규화·NULL·JOIN·그룹함수·윈도우함수): 5,000~7,000자
- **개념 정의 위주** (DML·DCL·집합연산자): 3,000~4,000자
- **부차적** (정규표현식·PIVOT): 2,500~3,500자

길이 격차 자체가 "사람이 우선순위를 매겨가며 썼다"는 신호. 단, 운영자 voice·연결어 추가하다 보면 자연 변별 발생할 가능성 높음. 무리해서 길이 맞추지 말 것.

## 6. 사이트 레벨 보강 (본문 외)

본문만 손대면 AdSense 재신청 통과 확률 50/50. 사이트 외곽도 같이 보강:

| 항목 | 현재 | 추가/수정 |
|---|---|---|
| About 페이지 | 없거나 약함 | 사이트 만든 이유, 데이터 출처(시험원 기출 등), 운영 방침 |
| 운영자 노트 / 블로그 | 없음 | 회차별 출제 분석 1~2개, "이번 회차에서 정답률 낮았던 문제" 같은 글 |
| 데이터 통계 페이지 | 없음 | 챕터별 학습자 정답률, 회차별 통과율 등 사이트 고유 데이터 |
| Privacy / Terms | 있음(추정) | 최신화 + 운영자 contact 명시 |
| Footer | (확인 필요) | 운영자명/연락처/사이트 운영 시작일 |

→ AdSense 리뷰어는 보통 샘플 본문 + About + Privacy + 1차 도메인 페이지를 본다. 본문 외곽 신호가 있으면 본문 톤 일부가 약해도 통과율 올라감.
