## 🚨 P0 — 명백한 오답 (즉시 수정)

### 1. **R60 Q15 — 정답 키 잘못됨**

```sql
SELECT * FROM T WHERE (사번, 회원번호) IN ((10005, 2003));
```

위와 **동일한 의미의 조건식**을 묻는 문제.

- 현재 정답 표기: `(사번=10005) OR (회원번호=2003)` (option 0) ❌
- **올바른 정답**: `(사번=10005) AND (회원번호=2003)` (option 1) ✅

**근거**: 튜플 IN은 `(A, B) IN ((x, y))` ⇔ `(A=x AND B=y)` 가 SQL 표준. 같은 시리즈의 R51 Q32, R53 Q24, R45 Q36 모두 **AND 형식**을 정답으로 처리하는 일관된 정답 패턴이며 R60 Q15만 OR로 표기됨. 데이터에 첨부된 explanation에도 *"원본 기출의 정답 표기를 그대로 보존한다"* 라고 메모되어 있어, **원본 기출 복원 단계에서 오타 또는 OCR 오류가 그대로 들어왔을 가능성**이 큼.

**조치**: `scripts/authored/round-60.json` 의 Q15 `correctIndex`를 `0` → `1`로 수정. 동시에 `src/data/rounds/round-60.ts` 재빌드 (`node scripts/build-quiz-bank.mjs`).

## ⚠️ P1 — 모호하거나 학습자에게 잘못된 멘탈 모델을 심는 문항

### 2. **R60 Q2 — "연관속성"이라는 비표준 용어**

직원 엔터티 4개 속성(사번, 생년월일, 연령, 부서코드) 중 성격이 다른 것을 묻고 옵션은 **파생속성 / 설계속성 / 기본속성 / 연관속성** (정답: 파생속성).

문제는 SQLD 표준 분류에서 "**연관속성**"이라는 용어 자체가 존재하지 않음.
- 특성 분류: **기본속성 / 설계속성 / 파생속성**
- 분해 여부: 단순속성 / 복합속성
- 엔터티 구성: PK속성 / FK속성 / 일반속성

옵션 4개 중 하나(연관속성)만 다른 분류 체계 또는 비표준 용어이므로 본 문제의 변별 기준이 흐림. 학습자는 "연관속성"을 외우면 안 됨.

**조치**: 옵션을 SQLD 표준 용어로 교체하거나, 정답을 "연관속성"(=비표준)으로 바꾸고 해설에 명시.

### 3. **R60 Q9 — "주식별자 선정과 가장 관련 적은 정규화"**

- 옵션: 1NF / 2NF / 3NF / BCNF (정답: 3NF)
- 그러나 1NF 도 주식별자 선정과 직접 관련은 약함 (atomic value 보장이지 키 선정 자체와 무관)
- 출제 의도가 "이행 종속을 다루는 3NF는 비주식별자 간 관계만 본다"는 점이라면, 옵션에서 1NF를 빼고 다른 보기로 대체해야 변별이 명확.

### 4. **R60 Q11 — 계층형 가상 컬럼 "전제조건 없이 단독 동작"**

- LEVEL / ISLEAF / ISCYCLE / CONNECT_BY_ROOT 모두 CONNECT BY 절이 있어야 동작.
- 정답이 "가, 나, 다, 라" 즉 모두인데 — 그렇다면 "전제 조건 없이 단독으로 동작하지 않는" 것이 아니라 "**4개 모두 계층형 컨텍스트가 필요**" 라고 표현해야 명확. 현 표현은 약간의 추가 차이(NOCYCLE 옵션 등)를 함의하는 것처럼 들려서 학습자가 헷갈림.

또한 **ISCYCLE은 NOCYCLE 옵션을 명시해야** 의미 있는 값을 반환하는데, 본문엔 NOCYCLE 언급이 없음. 추가 옵션이 있어야 동작하는 항목이라는 점을 해설로 보강 필요.

### 5. **R60 Q26 — 보기에 정답 힌트가 노출**

옵션 0번이 `ROWS UNBOUNDED PRECEDING (= ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)` 라고 적혀 있어서 **답을 그대로 알려줌**. 출제 의도는 학습자가 등치 관계를 알고 있는지를 묻는 것인데, 보기에 등치를 다 적어버림.

**조치**: 옵션 0을 단순 `ROWS UNBOUNDED PRECEDING` 으로 수정.

### 6. **R60 Q31 — FETCH FIRST without ORDER BY 의 결과 순서 단정**

해설: *"FETCH FIRST n ROWS ONLY는 정렬 조건이 없으면 물리적 저장 순서대로 상위 n건을 반환한다."*

이는 **SQL 표준에 어긋나는 단정**. 표준상 ORDER BY 없으면 결과 순서는 미정의(unspecified). Oracle/PostgreSQL 같은 구현체에서 통상 그렇게 보일 뿐, 인덱스/병렬/통계에 따라 달라질 수 있음. 학습자에게 "정렬 안 해도 입력 순서대로 나온다"는 잘못된 멘탈 모델을 심음.

**조치**: 해설을 *"ORDER BY 절이 없으면 결과 순서는 SQL 표준상 미정의이지만, 시험 답안 기준으로는 표시된 저장 순서대로 보고 답한다."* 로 표현 완화.

### 7. **R60 Q32 — "이미 값이 있는 NOT NULL 추가" 모호**

옵션 0: *"이미 값이 들어 있는 NOT NULL 제약을 추가하는 경우"* — Oracle 12c 이후 `DEFAULT`를 함께 지정하면 기존 NULL을 채우면서 NOT NULL 제약 추가 가능. 따라서 **항상 오류**는 아님. 옵션 표현이 너무 단정적.

### 8. **R60 Q39 — MERGE 문 결과 케이스 명시 안됨**

`MERGE INTO TGT ... USING SRC ...` 의 결과를 묻는데 **TGT의 초기 상태**(매칭/불매칭) 가 references 에 없음. INSERT 케이스인지 UPDATE 케이스인지 알 수 없는 상태에서 답 `100/100/100` 을 강제. UPDATE 케이스라면 V3는 손대지 않으므로 결과가 다름.

**조치**: references 에 "TGT 테이블이 비어있는 상태에서 SRC 의 행 1건을 처리한다" 등의 시나리오 추가.

### 9. **R60 Q46 — DENSE_RANK vs RANK 모호**

부서별 급여 상위 3명을 묻고 정답이 `DENSE_RANK`. 그러나 동률(ties) 시나리오가 명시되지 않으면 `RANK`도 답이 됨 — SQLD 모범답안에선 "상위 N명" 의도에 따라 둘 다 통용. 출제 의도가 "동률도 모두 포함" 이면 DENSE_RANK 가 맞지만 명시 필요.

## 🔁 800문항 자동 패턴 스캔 결과

명백한 SQL 트랩 패턴이 사용된 문항. 본 리포트에서 일일이 검수하지는 못했으나, 같은 회차 내 일관성 확인이 필요한 항목 리스트:

| 패턴 | 건수 | 추가 검수 필요 |
|---|---|---|
| `NOT IN (서브쿼리)` 와 NULL 트랩 | 12 | NULL 포함 여부에 따라 결과 달라짐 — 각 문항이 NULL 케이스를 명시했는지 확인 |
| 튜플 `(A,B) IN ((..,..))` 동등성 | 4 | 정답이 일관되게 AND 형식인지 (R60 Q15 같은 사고 재발 방지) |
| `ROWNUM` + `ORDER BY` | 10 | Oracle 의 ROWNUM 부여 시점 (WHERE 통과 후, ORDER BY 전) 트랩 — 인라인 뷰 사용했는지 |
| `ISCYCLE` 사용 시 `NOCYCLE` 누락 | 1 | R60 Q11 — NOCYCLE 명시 필요 |
| `correctIndex` 범위 외 | 0 | ✅ 양호 |
| 옵션 4개 미준수 | 0 | ✅ 양호 |

`HAVING SUM(...) IS NULL` 류 트랩, `OUTER JOIN` 의 ON vs WHERE 조건 위치 차이, `GROUP BY` 와 분석 함수의 중첩 등은 특히 정답이 모호해지기 쉬우므로, 회차별 동일 패턴 문항 간 정답 일관성 검토를 권장.

## 💡 콘텐츠 운영 측면 개선 제안

### A. 데이터 입력 검증 체크리스트
새 회차 추가 시 `scripts/build-quiz-bank.mjs` 실행 전 검증 단계 추가:
- [ ] `correctIndex` 가 0~3 범위 정수
- [ ] `options.length === 4`
- [ ] `explanation` 30자 이상 (또는 의도적 빈 값 표시)
- [ ] `references[].content` 에 `**`, `__` 같은 raw markdown 문자열 없음 (현재 R60 Q1 한 건 검출됨 — 우리 `renderInlineMD` 로 방어 됨)
- [ ] 같은 패턴 문항(튜플 IN, NOT IN+NULL 등)은 같은 회차 내 정답 형식이 일관

스크립트로 자동화 가능 (Backend 에이전트에 위임).

### B. 해설 보강 우선순위
1. **R47 (36문항 무해설)** — 가장 시급
2. R48 (26), R50 (21), R49 (18), R60 (18) 순으로 진행
3. 해설은 **왜 그 답인지 + 왜 다른 건 답이 아닌지**의 두 가지를 모두 담아야 학습 효과
4. 해설 없는 문항은 **풀이 모드에서 "이 문항은 해설 보강 중" 표시**를 띄워주는 게 신뢰 측면에서 더 좋음 — 사용자가 "왜 안 맞지" 하다가 이탈하는 걸 방지

### C. 콘텐츠 신뢰성 표시
- 푸터에 *"학습용 자료이며 실제 시험 문제와 동일하지 않습니다"* 는 이미 추가됨 ✅
- 회차별 헤더에 **"복원 정확도"** 표시 추가 권장 (예: "복원 출처: 수험생 후기 종합", "복원 정확도: 약 90%")
- 오답·해설 오류 신고 버튼 — **사용자가 직접 issue 를 raise 할 수 있게**. CS → PO → backend 의 피드백 루프와 연결.

### D. 출제 범위 점검
SQLD 2025 개정안 기준 출제 범위(데이터 모델링 10문항 + SQL 활용 40문항)와 현 문제 분포가 일치하는지:

```bash
# 자동 카운트 가능
node -e 'JSON.parse(...)["authored"].filter(q=>q.subject==="1과목").length'
```

코드상 CBT 빌더에서 1과목 10건/2과목 40건으로 강제하고 있어 분포는 보장되지만, 각 과목 내 단원별(엔터티/속성/관계/식별자/정규화·반정규화 등) 균형은 별도 점검 필요.

## 📎 부록: 검수 메소돌로지

이 리포트는 다음 방식으로 작성됨:

1. **R60 풀 검토** — 50문항 모두 한 줄씩 SQL/SQLD 정답 정합성 확인
2. **R47 무해설 다발 표본** — 5문항 깊이 검토
3. **800문항 패턴 스캔** — Node 스크립트로 알려진 트랩 키워드 검색 → 일관성 sniff test
4. **R45/R51/R53 동형 문제 비교** — R60 Q15 의 정답 오류 입증 근거

따라서 본 리포트는 **샘플링 + 자동 패턴 스캔 + 표적 정밀 검토**의 혼합. 800문항 전수 정답 검증을 위해서는 추가로 **각 회차별 1명 분량의 SQLD 공인 강사 인적 검수**(약 2일 × 인당)가 필요하며, 이는 본 자동화 검수의 후속으로 권장.
