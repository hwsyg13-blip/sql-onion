본질식별자 vs 인조식별자

업무 자연 도출 vs 인위적 부여. 보안·성능·일관성 균형을 맞추는 PK 선택

핵심 요약 정의

본질식별자는 업무에서 자연스럽게 도출된 식별자, 인조식별자는 인위적으로 만든 식별자다. 둘의 장단점을 알고 상황에 맞게 선택한다.
도서관에서 ISBN(출판사 부여 = 본질식별자)과 자체 분류번호 A-001(도서관 임의 부여 = 인조식별자) 두 가지로 책을 구분할 수 있다. ISBN이 길고 형식이 들쑥날쑥해서 도서관은 자체 번호를 더 자주 쓴다.

언제 무엇을 쓸까

현업 권장 패턴: PK는 인조식별자, 본질키는 UNIQUE 제약으로 별도 보존 → 보안·성능·일관성 모두 만족. 본질키를 PK로 쓰면 정규화 단계의 종속성 분석이 자연스럽지만, 변경 위험이 따른다는 점을 고려한다.

본질식별자 사용

CREATE TABLE BOOK (
    ISBN     VARCHAR2(20) PRIMARY KEY,  -- 본질식별자
    TITLE    VARCHAR2(200),
    AUTHOR   VARCHAR2(100)
);

인조식별자 사용

CREATE TABLE BOOK (
    BOOK_ID  NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,  -- 인조식별자
    ISBN     VARCHAR2(20) UNIQUE,                              -- 본질키는 UNIQUE로 유지
    TITLE    VARCHAR2(200),
    AUTHOR   VARCHAR2(100)
);

-- 같은 ISBN을 두 번 INSERT 시도
INSERT INTO BOOK(ISBN, TITLE) VALUES('978-89-1234', 'SQL');
INSERT INTO BOOK(ISBN, TITLE) VALUES('978-89-1234', 'SQL');
-- ORA-00001: unique constraint violated

SELECT * FROM BOOK;

↓ 결과

BOOK_ID (PK)ISBN (UQ)TITLEAUTHOR
1978-89-1234SQL(NULL)

→ 두 번째 INSERT는 ISBN UNIQUE 제약 위반으로 거부 → 1행만 남는다. 인조 PK + 본질키 UNIQUE 조합이 무결성을 함께 지켜준다.

권장 패턴: 인조식별자를 PK로, 본질식별자를 UNIQUE 제약으로 함께 둔다. UNIQUE 제약 덕에 같은 ISBN 중복 입력은 차단되어 본질키의 무결성도 보존된다.

Before & After 인조식별자 도입의 효과

회원 김철수의 주민번호(800101-1234567)를 회원 PK로 쓰는 경우와, 인조식별자(M01)를 PK로 두고 주민번호는 UNIQUE로 보존하는 경우. 자식 테이블(주문)에 어떤 값이 흩뿌려지는지를 비교한다.

Before — 본질식별자(주민번호)를 PK로

주문 (FK: 주민번호)
800101-1234567 → 김철수 주문 1
800101-1234567 → 김철수 주문 2

자식엔 짧은 ID만, 본질키는 UNIQUE로 보존

PK는 모든 자식 테이블에 FK로 흩어지므로, 본질식별자가 PK면 그 값(주민번호)도 함께 흩어진다 — 보안 사고의 표면적이 그대로 늘어나는 셈이다. 또 본질키는 길거나 형식이 들쑥날쑥해 인덱스·조인 비용도 커진다. 인조식별자(M01 같은 짧은 키)를 PK로 두고 본질키는 회원 테이블 한 곳에 UNIQUE로 가둬두면, 보안·성능·일관성이 한꺼번에 정리된다. 다만 본질키의 무결성 검증을 위해 UNIQUE 제약을 빼먹지 않는 것이 핵심이다.
