데이터 모델의 이해

현실 → 개념 → 논리 → 물리. 3가지 관점, 3층 스키마, 좋은 모델 6요소

핵심 요약정의

데이터 모델이란 현실의 정보를 데이터베이스(DB)에 담기 위해 그린 설계 도면이다.
회원·상품·주문 같은 정보를 어떻게 저장하고 연결할지 미리 그려보는 작업이다. 정보의 덩어리는 엔터티, 세부 항목은 속성, 엔터티 간 연결은 관계로 표현한다.

개념 도식화한 비즈니스가 데이터베이스가 되기까지

같은 쇼핑몰 사례가 단계별로 어떻게 구체화되는지 직접 본다.

STEP 1
개념적 모델 큰 그림
핵심 엔터티·관계 ERD. 속성·자료형은 아직 안 본다.
›
STEP 2
논리적 모델 속성·키
속성·PK·FK 채움 + 정규화. DBMS와 무관.
›
STEP 3
물리적 모델 실제 DBMS
CREATE TABLE + 인덱스·파티션·자료형 명시.
›
STEP 4
데이터베이스 운영
데이터가 차곡차곡 쌓인 상태. SQL로 조회·입력·수정.

1단계 — 개념적 모델 (큰 그림)

업무에서 다루는 핵심 명사(엔터티)와 그 사이의 연결을 큰 그림으로 그린다.

// 회원 1 : N 주문
// 주문 1 : N 주문상세  ←  N : 1 상품

2단계 — 논리적 모델 (속성·키·정규화)

각 엔터티의 속성을 채우고 PK·FK 를 정한다. 이 단계에서 정규화(1NF → 2NF → 3NF)도 함께 수행한다.

3단계 — 물리적 모델 (실제 DBMS 구현)

논리 모델을 실제 데이터베이스의 테이블로 만든다. 자료형·인덱스·제약조건을 명시.

CREATE TABLE MEMBER (
    MEMBER_ID  VARCHAR2(10) PRIMARY KEY,
    NAME       VARCHAR2(50) NOT NULL,
    PHONE      VARCHAR2(20)
);

CREATE TABLE PRODUCT (
    PROD_ID    VARCHAR2(10) PRIMARY KEY,
    PROD_NAME  VARCHAR2(100) NOT NULL,
    PRICE      NUMBER(10) NOT NULL
);

CREATE TABLE ORDERS (
    ORDER_ID   NUMBER PRIMARY KEY,
    MEMBER_ID  VARCHAR2(10) REFERENCES MEMBER(MEMBER_ID),
    ORD_DATE   DATE DEFAULT SYSDATE
);

CREATE INDEX IDX_ORDERS_MEMBER ON ORDERS(MEMBER_ID);  -- 성능용 인덱스

4단계 — 데이터베이스 (운영 중인 실제 데이터)

만든 테이블에 데이터가 차곡차곡 쌓인 상태. 사용자가 SQL 로 조회·입력·수정.

좋은 데이터 모델의 특징

1

3층 스키마 (ANSI/SPARC)

같은 쇼핑몰 데이터베이스를 세 가지 관점에서 본 모습. 누가 보느냐에 따라 같은 데이터가 전혀 다른 형태로 보인다.

EXTERNAL외부 스키마 — 각 사용자/앱이 보는 화면
여러 개 · 사용자·개발자 · SQL의 VIEW 또는 응용 프로그램의 가공 데이터
↑ 논리적 독립성 — 개념 스키마가 바뀌어도 외부 스키마는 영향 없음 ↑
CONCEPTUAL개념 스키마 — 조직 전체가 공유하는 ERD
1개 · DA(Data Architect) · 모든 화면의 원본이 되는 통합 설계도
↑ 물리적 독립성 — 내부 스키마가 바뀌어도 개념·외부 스키마는 영향 없음 ↑
INTERNAL내부 스키마 — 디스크 위 실제 저장 구조
1개 · DBA(DB Administrator) · 데이터 파일·인덱스·파티션·캐시

관점 1. 외부 스키마 (External) — 각 사용자/앱이 보는 화면

누가 본다화면 (View)보이는 컬럼 예시
김철수 (모바일앱)"내 주문 내역"주문번호 · 상품명 · 금액 · 주문일
이영희 (웹)"위시리스트"상품명 · 가격 · 이미지
관리자 (백오피스)"일별 매출"날짜 · 총매출 · 주문건수

관점 2. 개념 스키마 (Conceptual) — 조직 전체가 공유하는 ERD

위 모든 화면의 원본이 되는 하나의 통합 설계도. 회원·상품·주문·주문상세·결제·배송 등 모든 엔터티와 관계. 설계자(DA)가 관리하는 전사 데이터 모델. 데이터베이스에 단 하나만 존재.

관점 3. 내부 스키마 (Internal) — 디스크 위 실제 저장 구조

개념 스키마가 물리적으로 어떻게 저장되는가. DBA·DBMS의 영역.

항목예시
데이터 파일/oracle/data/SHOP_DATA01.dbf (8KB 블록 단위)
인덱스IDX_ORDERS_MEMBER (B-Tree, 회원ID 정렬)
파티션ORDERS 테이블을 월별로 분할 (P_2026_04, P_2026_05 ...)
캐시자주 조회되는 회원 데이터 메모리 캐시

3층이 분리된 이유 — 데이터 독립성

스키마관점개수누가 다룬다
외부 (External)사용자·응용 프로그램여러 개사용자·개발자
개념 (Conceptual)설계자 통합1개DA (Data Architect)
내부 (Internal)물리 저장1개DBA (DB Administrator)

데이터 독립성 2가지

종류의미
논리적 독립성개념 스키마가 변경돼도 외부 스키마(응용)는 영향 없음
물리적 독립성내부 스키마가 변경돼도 개념·외부 스키마는 영향 없음

SQL 실전모델이 곧 테이블이 된다

논리 모델의 PK는 물리 모델에서 식별자(PRIMARY KEY 제약)가 된다.

-- 논리 모델의 '고객' 엔터티 → 물리 모델의 CUSTOMER 테이블
CREATE TABLE CUSTOMER (
    CUST_ID    VARCHAR2(10) PRIMARY KEY,  -- 식별자
    CUST_NAME  VARCHAR2(50) NOT NULL,     -- 속성
    PHONE      VARCHAR2(20)               -- 속성
);

-- 외부 스키마(VIEW) — 응용 프로그램이 보는 화면
CREATE VIEW V_MY_ORDER AS
SELECT O.ORDER_ID, O.ORD_DATE, M.NAME
  FROM ORDERS O JOIN MEMBER M ON M.MEMBER_ID = O.MEMBER_ID;

↓ V_MY_ORDER 조회 결과 (외부 스키마가 보는 화면)

ORDER_IDORD_DATENAME
10012026-04-01김철수
10022026-04-05이영희

개념 스키마(MEMBER + ORDERS 두 테이블)는 그대로지만, VIEW를 통해 외부 스키마는 "주문번호·날짜·이름" 한 화면처럼 보인다 — 같은 데이터를 보는 관점이 다른 것뿐이다.
