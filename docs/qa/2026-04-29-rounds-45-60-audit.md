## 3. 처리 결과

### 3.1 R50 #5 정답 노출 — fix 완료

**문제**: 1과목 #5 "발생 시점 기준 중심 엔터티에 해당하는 예는?" — 정답 ③ 프로젝트.
**leak**: text reference 의 분류 설명에 `중심(Main) 엔터티: ... — 계좌, 프로젝트, 계약` 형태로 정답이 그대로 박혀있음. 사용자가 reference 를 펼치면 답을 즉시 본다.
**fix**: text reference 의 예시 목록을 모두 제거하고 일반 정의로 압축.
- 변경 전: `"• 중심(Main) 엔터티: 기본 엔터티에서 발생, 다른 행위 엔터티의 부모 — 계좌, 프로젝트, 계약"`
- 변경 후: `"• 중심(Main) 엔터티: 기본 엔터티로부터 발생하며, 다른 행위 엔터티의 부모가 된다."`
- 적용 파일: `scripts/authored/round-50.json`, `src/data/rounds/round-50.ts` (build-quiz-bank.mjs 재실행)
- 재검사: `check-answer-leak` 19건 → 18건 (R50 #5 제거 확인)

### 3.2 SQL 결과 평가형 18건 — false positive 처리

위 §2.2 의 18건은 출제 의도상 옵션이 SQL 표현식이거나 SQL 실행 결과이며, reference SQL 은 옵션을 *평가하는 자료*다. 정답이 reference 안에 있는 게 자연스럽고, 학습자는 SQL 실행 결과를 추론해야 정답을 알 수 있다. **fix 대상 아님** — 단, 이 패턴이 학습 모드에서 답 hint 가 될 수 있다면 차후 PO 가 "정답 검증용 reference 는 정답 풀이 후 노출" 같은 UX 정책을 정할 수 있음 (별도 채팅).

### 3.3 SHORT_EXPLANATION 43건 — 인계 (자동 보충 보류)

자동으로 해설을 길게 늘리면 도메인 정확성 위험이 큼. 인간 도메인 검수자가 회차별로 보강해야 안전. 현재 짧은 해설은 잘못된 게 아니라 *간결한* 것 — 정답성에는 영향 없음. 우선순위 P2.

### 3.4 R55 #35 ABSTRACT_OPTIONS — 인계 (출제 패턴 보존)

옵션이 "(1), (2), (3), (4)" 단순 라벨. SQL 자체는 reference 의 sql.code 안에 `-- (1) INSERT...` 형태로 있음. 사용자는 옵션 보고 reference SQL 에서 (1)~(4) 찾아가야 함. **읽기 흐름이 끊김**.

수정 옵션:
- (a) reference SQL 의 (1)~(4) 를 분리해 별도 ref 또는 옵션에 풀 SQL 표시 — *원본 시험 형태 변경*
- (b) reference SQL 에 시각적 구분(빈 줄 + 라벨) 강조 — 보존 + 가독성 ↑
- (c) 그대로 두고 explanation 에서 (4)의 SQL 을 한 번 더 인용 — 가장 안전

권장: (c) — 최소 변경. 다음 채팅 인계.

### 3.5 R56 #22 MISSING_REFERENCES — false positive 판단

title 이 "다음 중 결과가 나머지와 다른 것은?" 으로 "결과" 키워드 매칭됐지만, 옵션 자체가 SQL 표현식 4개라 *옵션이 reference 역할*을 한다. 별도 reference 불필요. **fix 대상 아님**.

### 4.5 도메인 정답성 검수의 한계

자동 도구로는 *형식*만 검사 가능. 다음은 *반드시 인간 도메인 검수* 필요:
- 정답 옵션이 진짜 정답인가 (예: SUBSTR 결과가 정확한가, JOIN 결과가 옳은가, 정규형 정의가 정확한가)
- 옵션 두 개가 동시에 정답 가능한지 (CS 제보 R58 #3 같은 케이스)
- stem 의 ERD/SQL 자료가 옵션을 풀기에 충분한가

이건 16회차 × 50문항 × 1~2분 = **순수 인간 시간 13~25시간**의 작업이고, AI 가 도메인 검수해도 환각 위험으로 인간 재검토 필수.

**권고**: 사용자(또는 SQLD 자격증 보유자)가 회차당 30분 페이스로 직접 풀어보면서 검수하는 게 가장 신뢰성 높음. 본 audit 문서는 그 작업의 *시작점*과 *중간 합류점*을 제공하기 위함.
