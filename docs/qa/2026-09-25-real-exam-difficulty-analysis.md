# 실제 SQLD 시험이 복원 문제보다 어렵게 느껴지는 이유와 보완 방안 (2026-09-25)

## 0. 결론 (한 줄)
**"새로운 개념"이 어려운 게 아니라, 아는 개념 2~3개를 꼬아 놓고(NULL·서브쿼리·형변환·수행순서), 보기를 그럴듯하게 만들어 헷갈리게 하며, 1과목은 정보가 부족한 모델링 판단을 시키는 방식**으로 어려워졌다. 그런데 복원 문제는 기억 기반이라 이 "꼬임"과 "그럴듯한 오답"이 가장 먼저 사라진다.

## 2. 어디가 어려운가

| # | 어려움의 원인 | 근거 | 우리 문제에서의 상태 |
|---|---|---|---|
| 1 | **개념 결합형(꼬기)**: NULL × NOT IN × 집합연산, 집계 × 형변환 × 묵시적 형변환, 논리적 수행 순서 × 별칭 | 데이널 62회(MAX(TO_CHAR) 예), 정미나(NOT IN+NULL) | 최근 회차(60~62)는 3개념 이상 결합 문항이 회차당 2.7개로 늘었지만(45~52회 1.9개), 여전히 소수 |
| 2 | **NULL 의존도**: 회차당 NULL 관련 문항이 11개 안팎, 여러 영역에 섞임 | 데이널 62회, 우리 측정 45~52회 11.4 → 60~62회 15.7 | 개념형 단독 문항은 있으나 "NULL이 다른 영역에 섞인" 문항이 부족 |
| 3 | **효자 문제 소멸**: 지문 없는 개념형(2과목) 비율이 줄고 계산형이 늘어남 | 정미나. 우리 측정: 회차당 개념형 8.0 → 5.3, 표+SQL 계산형 13.6 → 16.7 | 데이터에도 같은 경향이 있음(복원 자체는 반영됨) |
| 4 | **그럴듯한 오답(보기 설계)**: 결과 행 수·순서·NULL 위치만 다른 비슷한 SQL 4개, 정답 노출 없는 결과형 보기 | 정미나("맞았는지 확신이 안 선다") | 복원본은 오답이 쉽게 걸러지는 형태가 많음(개념형 보기 재작성·정답 노출 제거 과정에서 더 단순해짐) |
| 5 | **처음 보는 구문을 해석으로 풀기**: MERGE, INSERT FIRST, PIVOT/UNPIVOT, REGEXP_REPLACE, OFFSET FETCH, 윈도우 프레임 | 정미나 61회("모르는 구문 나와도 해석"), 62회 INSERT FIRST/UPDATE 서브쿼리 | 다룬 구문의 종류가 회차마다 조금씩 다름, 심화 세트로 일부 보강 |
| 6 | **1과목의 모호한 모델링 판단**: 마이너 표기법(바커·피터 첸·UML), 상호 배타 관계, 정보 부족한 정규화 판단(2NF vs 3NF), 식별/비식별 | 데이널 60·61·62회 1과목 3편 | 1과목은 개념 정의형 위주라 "가장 적절한 것" 판단형이 적음 |
| 7 | **시간 압박**: 50문항/90분, 긴 SQL·표를 머릿속으로 시뮬레이션 | DC 후기, kgosu 후기 | 앱에 문항별 소요 시간 정보가 없음 |
| 8 | **1과목 과락 리스크**: 10문항 중 4개 미만이면 불합격 | 데이널 60·61회 | 1과목 모의 진행률·과락 경고 기능 없음 |

## 3. 복원 문제가 쉽게 느껴지는 이유 (구조적)
1. **기억에 남는 문제만 남는다**: 표·SQL이 긴 문제나 미세한 조건 문제는 복원이 어렵다. recall.sqld.kr의 62회 초안에도 "보기 원문 복원 중", "임시 복원 상태" 문항이 다수였다.
2. **복원 중 단순화**: 조건·데이터가 기억나지 않으면 "논리는 맞지만 더 쉬운" 형태로 재구성된다(문어CBT 16번의 "급여가 모두 다르다" 같은 전제 추가).
3. **우리 쪽 편집이 더한 영향**:
   - 정답 노출 제거·보기 재작성으로 오답이 단순해짐.
   - 2026-09-21 커밋(`7a7c801`)이 중복 제거를 이유로 60회 1·28번 등을 **실제 기출이 아닌 문제로 교체**(영상 대조로 확인, `2026-09-25-round60-video-comparison.md`).
4. **규모는 문제가 아님**: 화면으로 확인한 61회의 평균 표 행 수(5.9행)·SQL 길이(119자)는 다른 회차와 비슷했다. 실제 시험이 어려운 이유는 **데이터 크기가 아니라 함정 밀도와 헷갈림**이다.

## 4. 문제 보완 방안

### A. 콘텐츠 (신규·수정)
| 우선순위 | 작업 | 상세 |
|---|---|---|
| 1 | **기출 충실도 복원** | 60회 영상 대조 결과(1·4·5·6·28·49번 등) 반영, 교체된 다른 회차 문항 14개도 원문과 대조. 변형 문항은 별도 풀로 이동 |
| 2 | **결합형 심화 세트 확대** (현재 32문항 → 150문항 목표) | NULL × (서브쿼리·조인·집합·집계·정렬·함수) 조합, 형변환 × 집계 × 비교, 수행순서 × 별칭 × 정렬, 등가 SQL 4개 비교("결과가 다른 것") — 표 2~3개 + 결과형 보기 |
| 3 | **오답 설계 규칙 도입** | 오답은 "완전히 틀린 것" 대신 **조건 하나만 다른** 결과(NULL 위치, 행 수 ±1, 정렬 순서, DISTINCT 유무)로 구성. 정답 위치는 무작위 |
| 4 | **낯선 구문 해석 세트** | MERGE, INSERT FIRST/ALL, PIVOT/UNPIVOT, REGEXP_*, OFFSET FETCH, ROWS/RANGE 프레임, LISTAGG, 계층 CONNECT_BY_* 를 "모르는 구문이라도 영어로 해석하면 풀리는" 형태로 |
| 5 | **1과목 판단형 보강** | ERD 표기법 3종 비교(IE/바커/피터 첸), UML 연관·의존, 상호 배타 관계, "정보가 부족한" 정규화 판단, 식별↔비식별 전환 기준을 "가장 적절한 것" 형태로 신규 작성 |
| 6 | **문항 "한 번 더" 변형** | 강사 권고("조건이 달라졌을 때 결과가 왜 달라지는지") — 계산형 기출마다 조건 1개만 바꾼 변형 1개를 짝지어 해설에 연결 |

### B. 검증 (품질)
- 모든 신규 SQL 문항은 `scripts/audit/verify-sql-answers.py`로 자동 정답 검증(현재 hard-mock 32문항 중 16문항 자동 검증 통과, 나머지 손 검산). Oracle 전용 구문 커버리지 확대가 과제.
- 신규 문항 작성 시 "정답 노출 없음·정답 위치 분산·오답이 서로 다른 결과값을 냄"을 스크립트로 점검.

### C. 앱 기능 제안 (기능 개발 채팅 범위)
1. 문항별 소요 시간 기록 → 회차 완료 후 "오래 걸린 문제" 복습(시간 압박 훈련)
2. 1과목 과락 경고(10문항 중 4문항 미만) 및 1과목 전용 미니모의
3. 계산형 문항에 "직접 실행해 보기"(브라우저 내 SQLite) — 강사들이 공통으로 권하는 "결과를 눈으로 확인" 학습을 앱 안에서
4. 난이도 라벨(L1~L4)을 지수화: 결합 개념 수, 표 개수, 보기 유사도로 자동 산정 → "실전 난이도 모의고사" 구성
5. 복원 회차 점수와 실전 점수의 괴리 안내(합격률 약 26%였던 회차 기준으로 "복원 기출 80점 이상 권장" 같은 보정 문구는 실제 사용자 데이터로 근거를 확보한 뒤 적용)

### D. 운영
- 시험 직후 응시자 제보를 회차별로 모으는 채널(recall.sqld.kr 방식)을 참고해, 복원 문항에 **"제보 일치율"**을 표시하고 낮은 문항은 별도 경고 처리.
- 문항별 정답률·오답 선택률을 수집(로그인 도입 이후)해 난이도 지수를 실측으로 보정.
