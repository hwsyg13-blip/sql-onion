# SQLD양파 콘텐츠 개선 가이드

문제(기출·모의고사)와 이론을 고칠 때 따르는 기준이다. 사람이든 에이전트든 콘텐츠를 고치기 전에 이 문서를 먼저 읽고, 여기 기준에 맞는지로 판단한다.

- 만든 날: 2026-11-05
- 근거: 사용자 피드백(아래 1장), 기출 900·모의고사 1156 전수 검토에서 나온 결함, 이론 개편 회귀 사고, 서치 콘솔 데이터
- 고치는 방법: 기준이 바뀌면 이 문서부터 고치고, 바뀐 이유를 1장 표에 한 줄 추가한다.

---

## 0. 판단 원칙 — 무엇이 먼저인가

1. **정확성**: 정답·해설·이론 내용이 틀리지 않는다. 다른 모든 것보다 먼저다.
2. **출제 범위**: 기출에 나온 개념이 이론에 빠짐없이 있다. 짧게 만들려고 빼지 않는다.
3. **이해하기 쉬움**: 처음 보는 사람이 예시로 먼저 감을 잡고, 표로 정리한다.
4. **표현**: 문제집처럼 자연스러운 말. AI 가 쓴 티가 나는 틀을 피한다.

이 순서가 충돌하면 앞의 것을 지킨다. 예를 들어 표현을 다듬다가 개념이 빠지면 안 된다.

**기준 문서**: 정답 판단은 수험자 입장에서 *SQL 전문가 가이드*(한국데이터산업진흥원)를 따른다. 실제 DBMS 동작과 다르면 가이드를 따르고, 해설에 DBMS 차이를 한 줄 적는다.

**시험 기간**: 시험 7일 전부터 시험일까지는 이론의 구조·문장을 크게 바꾸지 않는다. 정답이 틀린 것, 사실 오류만 고친다. 다음 시험일은 `src/lib/examDate.ts` 를 본다.

## 2. 문제(기출·모의고사) 기준

### 2-1. 문항이 갖춰야 할 것

- [ ] **정답이 정확히 하나**다. 다른 보기를 하나씩 대 봐도 정답이 둘이 되지 않는다.
- [ ] **문제 문장·자료·보기가 서로 맞는다.** 표 제목 = SQL 의 테이블명, 표 컬럼명 = SQL 컬럼명, 행 순서 = 해설의 계산 순서.
- [ ] **자료만 보고 풀 수 있다.** 빠진 SQL·조건이 없다. 그림 번호만 남은 보기는 글이나 표로 복원한다.
- [ ] **정답 힌트가 없다.** 표 제목·캡션에 정답이 드러나지 않는다(`check-answer-leak`).
- [ ] **실명·회사명이 없다.** "OO은행", "A사".
- [ ] **DBMS 가 갈리는 내용은 기준을 밝힌다.** 예: UNIQUE 의 NULL 개수, `||` 와 NULL, TO_DATE 기본값.

### 2-2. 복원 문항을 고칠 때

원문을 알 수 없는 복원 문항은 "원문 대기"로 두지 않는다. 수험자가 헷갈리지 않게 **단일 정답 문항으로 고치고**, 해설 끝에 `※` 로 고친 내용을 적는다. 정답 번호를 바꿨다면 해설에 이전 번호를 남기지 않는다(`audit-content` 가 잡는다).

### 2-3. 해설 쓰는 법

순서는 **정답 근거 → 오답 이유 → (있으면) 함정·DBMS 차이**.

1. 정답이 왜 맞는지: 계산 문제는 중간 값을 적는다. "A 7000, B 1000 이므로 …"
2. 나머지 보기가 왜 틀렸는지: 보기 번호를 붙여 한 문장씩. "② 는 RANK 의 결과, ③ 은 오름차순으로 매긴 결과다."
3. 시험에서 같은 함정이 다시 나올 수 있으면 한 줄.

- 말투는 "-다" 체로 통일한다.
- 정답 번호를 해설에 적을 때는 반드시 실제 정답 번호와 맞는지 확인한다.
- 길이 기준은 없다. 대신 오답 이유가 빠지면 미완성으로 본다.

### 2-4. 문제를 고친 뒤 검사

`validate-rounds --strict` · `check-question-quality` · `check-answer-leak` · `verify-sql-results`(mismatch 0) · `audit-content`(새 후보 0). 모의고사 풀은 고친 뒤 문항 수(현재 1156)가 그대로인지 확인한다.

## 3. 이론 기준

### 3-1. 챕터 구성

```
핵심            이 챕터를 한두 문장으로. 시험에서 무엇을 묻는지.
1. 섹션 제목     (문장형, 3-4 참고)
   도입 설명     일상 예시로 "무슨 말인지" 먼저 2~4문장
   표·도식·예제   정리. 예제 SQL 은 결과 표까지
   포인트        헷갈리는 한 가지
2. 섹션 …
함께 보기        관련 챕터 링크
30초 정리       시험 직전에 볼 3~4줄
```

### 3-2. 쉽게 쓰기

- **표만 두지 않는다.** 표 앞에 도입 설명을 둔다. 표 안의 짧은 구절("현실을 일정한 형식으로 · 쉬운 표기법으로")만으로는 처음 보는 사람이 이해하지 못한다.
- 도입 설명은 일상 예시로 시작한다. 예: 모델링 3단계 = 집 짓기 순서, 트랜잭션 = 계좌 이체, PIVOT = 엑셀 피벗.
- 계산이 들어가는 개념(ROLLUP 행 수, 윈도우 범위, SAVEPOINT)은 **예제 데이터 → SQL → 결과 표**를 모두 보여 준다.
- 도식은 인라인 SVG 로 그린다(앱·정적 페이지 모두 보임). 모바일 390px 에서 가로로 넘치지 않고, 다크 모드에서 글자가 보여야 한다.

### 3-3. 출제 범위 — 빼지 않는다

- **기출에 나온 개념은 이론에 반드시 있다.** 기출 900문항에 등장하는 SQL 키워드 121개 중 이론에 없는 것은 현재 1개(`KEEP`, 2문항)다.
- 이론을 줄이거나 다시 쓸 때는 4-2 의 전후 비교를 반드시 한다. 2026-11-02 개편에서 본문이 35%, 표가 302→80개로 줄면서 격리 수준·윈도우 범위·뷰 같은 출제 개념이 빠졌고, 학습자가 먼저 알아챘다.
- 새 회차 기출이 들어오면 그 회차의 SQL 키워드를 이론과 대조한다(INSERT FIRST·IDENTITY·IFNULL 을 이렇게 찾았다).

### 3-4. 표현 — 피할 것

| 피할 것 | 예 | 이렇게 |
|---|---|---|
| "X = Y" 식 제목 | 데이터 모델 = DB 설계도 | 데이터 모델은 데이터베이스의 설계도다 |
| 줄표(—)로 붙인 부제 | 순위 함수 — 급여 500, 400 … | 순위 함수 세 가지 |
| 모든 섹션에 같은 태그 | 꼭 외울 것 ① ② ③ | 1, 2, 3 번호 |
| 명사만 나열한 제목 | 만들어지는 그룹 | 세 연산자가 만드는 집계 단위 |
| 상투어 | "핵심을 짚어 보겠습니다", "~에 대해 알아봅시다" | 바로 내용으로 |
| 사실이 아닌 권위 | 가짜 저자·후기·"AI 생성" 표기 | 쓰지 않는다 |

`npm run build && node scripts/check-content-tone.mjs` 로 반복 문장·상투어를 확인한다.

### 3-5. 기출 함정은 이론에 넣지 않는다

- 이론 본문에 기출 문제·보기·"왜 틀렸나" 상자를 넣지 않는다(2026-11-05 사용자 결정, 119개 제거). 문제 맥락 없이 일부만 옮기면 이해가 안 된다.
- 기출을 이론에서 쓰고 싶으면, 그 문제의 핵심 규칙을 본문 설명이나 포인트 한 줄로 녹인다. 예: "RANGE 의 ±2 는 앞뒤 2행이 아니라 값이 2 차이 나는 행까지다."
- 기출을 직접 풀어 보는 것은 CBT·회차 화면의 몫이다. 이론은 개념을 이해시키는 데 집중한다.

### 3-6. 링크

- 다른 챕터의 개념이 본문에 처음 나오면 그 챕터로 링크한다(`<a href="#" data-chapter="cXXX">`). 정적 페이지에서는 빌드가 `/theory/cXXX/` 로 바꾼다.
- 챕터 끝에 "함께 보기" 로 관련 챕터를 묶는다.
- 개편 전후 링크 수를 비교한다. 2026-11-02 개편에서 81개가 0개가 됐는데 아무 검사도 못 잡았다.

## 4. 고치는 절차

### 4-1. 무엇부터 고치나

1. 학습자 제보·메일로 들어온 오류
2. 정답 불성립·복수 정답·풀 수 없는 문항
3. 해설이 정답과 다른 번호를 가리키는 것, 사실 오류
4. 이론에서 빠진 출제 개념
5. 해설의 오답 이유 보강, 이론 도입 설명
6. 표현 다듬기

### 4-2. 이론을 고치기 전후 비교 (필수)

| 비교 항목 | 기준 |
|---|---|
| 기출 SQL 키워드 중 이론에 있는 비율 | 줄어들면 안 됨 |
| 챕터 간 링크 수 | 줄어들면 안 됨 |
| 표·도식 수 | 크게 줄면 이유를 PR 에 적음 |
| 본문 글자 수 | 30% 넘게 줄면 빠진 개념 목록을 PR 에 적음 |

### 4-3. 내보내기 전

- 검사기 통과(2-4), 모바일 390px·다크 모드 화면 확인
- PR 본문에 무엇을 왜 바꿨는지, 전후 비교 수치
- 학습자가 외운 내용이 바뀌는 수정(정답 변경, 개념 설명 변경)은 수정 내역으로 알린다
